# 中国大陆云备份与管理员后台：技术设计 v0.1

> **非生产实现。** 这是后续版本的接口/权限合同，不是已上线的云服务。当前 v0.4 小程序不得导入 `future/cloud`、不得在未取得授权时上传用户数据。本设计须经过大陆主体、服务类目、备案、法务与安全评估后才能落地。

## 1. 交付顺序

- 账号：微信登录、短信验证码登录及账号关联。认证主体由服务端确定，不能直接相信客户端传来的 `userId`。
- 备份：由用户**主动开启**并可关闭。先做手动快照备份、恢复，再做自动备份，最后做多设备事件级同步。
- 管理员：独立内网/后台身份体系，区分工单客服、安全审查、超级管理员、审计；无工单或合法必要的案件，不许阅读用户正文。
- 部署：优先在中国大陆地域，做好实名资质、备案、隐私规则、数据处理合同、安全监测和事故响应。正式平台账号是否支持所需能力，待实际核对。

## 2. 保留既有记录模型

目前 `src/core/model.ts` 使用 `Records(version:1)`。云端快照仍包含 `days`、完整 `events`、`theme`，并通过 `validate` 及 `sha256(canonical(...))` 进行格式和传输完整性检查；**SHA-256 不是身份认证或防恶意伪造的签名**。

服务端推荐最小表：`users`、`auth_identities`、`devices`、`cloud_snapshot_versions`、`record_events`、`sync_cursors`、`backup_consents`、`deletion_requests`、`support_cases`、`safety_cases`、`staff_members`、`access_grants`、`admin_audit_events`。应按数据最小化设计索引、保留期限、访问控制。

## 3. 手动云备份协议（先做这一阶段）

服务端可设计如下语义（URL 仅为待实现接口，当前**不可调用**）：

| 请求 | 行为 | 约束 |
| --- | --- | --- |
| `POST /v1/backup/consent` | 用户主动启用或撤回云备份 | 身份已验证，记录版本化告知与合法性依据 |
| `GET /v1/backup/snapshot` | 下载属于当前登录用户的最新备份 | 从已验证会话获取 owner，禁止客户端越权指定其他用户 |
| `PUT /v1/backup/snapshot` | 提交完整历史快照及 `baseRevision`、`baseDigest` 和 `idempotencyKey` | 服务端事务中比较版本、校验历史不被截断、记录幂等回执 |
| `DELETE /v1/backup/snapshot` | 用户请求删除云备份 | 规定副本删除计划及法律所要求的例外 |
| `GET /v1/backup/status` | 最近成功备份时间/版本/失败状态 | 不得把“提交中”显示为“已同步” |

冲突返回 **409**，携带当前版本/摘要及明确的“保留双方数据”选项；禁止静默最后写入胜出。幂等标识按用户隔离，**必须**用数据库事务与唯一约束实现，示例内存 `CloudContractSimulator` 不能代替原子性保证。服务端对旧 `events` 保留前缀；用户合法修改须通过新增事件，不得删除原有旧文字。恢复历史版本应设计为明确的新分支/恢复事件，不能偷换快照。

## 4. 管理员最小授权模型

服务端所有正文读取请求执行以下检查，任何一项不满足默认拒绝：

1. 员工身份验证和多因素验证，角色为客服或安全审核员；超级管理员默认**不是**正文阅读角色。
2. 存在开放的具体工单或必要安全审核案件，目的与角色对应。
3. 授权属于该员工、该案件、该用户、**指定日期范围**；由不同员工审批，未过期、未撤销，示例中最长为两小时。
4. 阅读理由、主体、范围、时间和结果写入可保护的审计存储；不记录正文。生产环境需要保证**访问决定与审计写入的可靠关联**，审计故障应拒绝敏感读取。
5. 不能用管理员前端按钮的显示状态作为权限检查。所有接口服务端验证；处理人员不能凭普通用户 ID、工单编号猜测他人记录。

`future/cloud/adminAccessContract.ts` 仅返回允许/拒绝和脱敏审计事件模板。正式服务必须使用可信数据库案件/授权记录、独立审批、多因素登录、审计数据防篡改、异常访问告警，确保实际读取**不能绕过**此策略。

## 5. 安全与合规前置核对

| 核验事项 | 当前状态 |
| --- | --- |
| 真实中国大陆个人/经营主体及云服务适用资质 | 待确认 |

| 微信登录、手机号能力及短信签名资格 | 待正式 AppID 验证 |

## 6. 目前的代码与验收范围

- `future/cloud/snapshotContract.ts`：纯内存服务器协议模拟，主动开启标记、owner 隔离、幂等、冲突、历史保全；**没有 HTTP、账号、数据库或自动上传代码**。
- `future/cloud/adminAccessContract.ts`：授权决策原型；不暴露真实管理后台或读取接口。
- `tests/check-future-cloud-contracts.mjs`：使用虚构记录模拟多个账号、并发/重放/篡改及员工权限失败情形；独立运行与 CI 持续验证。
- 两个合同模块不在 `src/` 内，不会被 H5/小程序打包；v0.4 首发仍只使用本地 `Records` 和用户主动的 JSON 备份。

**进入真正后端开发的门槛**：先确认主体和云供应商选型、正式账号能力、隐私/授权模型，以及完整事务、数据删除、日志与权限测试方案。不得用这个原型对真实用户开放云备份。
