# 中国大陆云备份与管理员后台：技术设计 v0.1

> **非生产实现。** 这是后续版本的接口/权限合同，不是已上线的云服务。当前 v0.4 小程序不得导入 `future/cloud`、不得在未取得授权时上传用户数据。本设计须经过大陆主体、服务类目、备案、法务与安全评估后才能落地。

## 1. 交付顺序

- 账号：微信登录、短信验证码登录及账号关联。认证主体由服务端确定，不能直接相信客户端传来的 `userId`。
- 备份：由用户**主动开启**并可关闭。先做手动快照备份、恢复，再做自动备份，最后做多设备事件级同步。
- 管理员：独立内网/后台身份体系，区分工单客服、安全审查、超级管理员、审计；无工单或合法必要的案件，不许阅读用户正文。
- 部署：优先在中国大陆地域，做好实名资质、备案、隐私规则、数据处理合同、安全监测和事故响应。正式平台账号是否支持所需能力，待实际核对。

## 2. 保留既有记录模型

目前 `src/core/model.ts` 使用 `Records(version:1)`。云端快照仍包含 `days`、完整 `events`、`theme`，并通过 `validate` 及 `sha256(canonical(...))` 进行格式和传输完整性检查；**SHA-256 不是身份认证或防恶意伪造的签名**。

服务端推荐最小表：`users`、`auth_identities`、`devices`、`cloud_snapshot_versions`、`record_events`、`sync_cursors`、`backup_consents`、`deletion_requests`、`support_cases`、`safety_cases`、`staff_members`、`access_grants`、`admin_audit_events`。应按数据最小化设计索引、保留期限、访问控制。

## 3. 手动云备份协议（先做这一阶段）

服务端可设计如下语义（URL 仅为待实现接口，当前**不可调用**）：

| 请求 | 行为 | 约束 |
| --- | --- | --- |
| `POST /v1/backup/consent` | 用户主动启用或撤回云备份 | 身份已验证，记录版本化告知与合法性依据 |
| `GET /v1/backup/snapshot` | 下载属于当前登录用户的最新备份 | 从已验证会话获取 owner，禁止客户端越权指定其他用户 |
| `PUT /v1/backup/snapshot` | 提交完整历史快照及 `baseRevision`、`baseDigest` 和 `idempotencyKey` | 服务端事务中比较版本、校验历史不被截断、记录幂等回执 |
| `DELETE /v1/backup/snapshot` | 用户请求删除云备份 | 规定副本删除计划及法律所要求的例外 |
| `GET /v1/backup/status` | 最近成功备份时间/版本/失败状态 | 不得把“提交中”显示为“已同步” |

冲突返回 **409**，携带当前版本/摘要及明确的“保留双方数据”选项；禁止静默最后写入胜出。幂等标识按用户隔离，**必须**用数据库事务与唯一约束实现，示例内存 `CloudContractSimulator` 不能代替原子性保证。服务端对旧 `events` 保留前缀；用户合法修改须通过新增事件，不得删除原有旧文字。恢复历史版本应设计为明确的新分支/恢复事件，不能偷换快照。

## 4. 管理员最小授权模型

服务端所有正文读取请求执行以下检查，任何一项不满足默认拒绝：

1. 员工身份验证和多因素验证，角色为客服或安全审核员；超级管理员默认**不是**正文阅读角色。
2. 存在开放的具体工单或必要安全审核案件，目的与角色对应。
3. 授权属于该员工、该案件、该用户、**指定日期范围**；由不同员工审批，未过期、未撤销，示例中最长为两小时。
4. 阅读理由、主体、范围、时间和结果写入可保护的审计存储；不记录正文。生产环境需要保证**访问决定与审计写入的可靠关联**，审计故障应拒绝敏感读取。
5. 不能用管理员前端按钮的显示状态作为权限检查。所有接口服务端验证；处理人员不能凭普通用户 ID、工单编号猜测他人记录。

`future/cloud/adminAccessContract.ts` 仅返回允许/拒绝和脱敏审计事件模板。正式服务必须使用可信数据库案件/授权记录、独立审批、多因素登录、审计数据防篡改、异常访问告警，确保实际读取**不能绕过**此策略。

## 6. 真实 PostgreSQL 后端验证（仍为未公开的隔离工程）

后续云后端现在已有**非生产的真实数据库基础实现**，不仅是内存合同：

- `future/server/sql/001_initial.sql`：快照、备份启用与通知版本、提交幂等回执、客服/审核案件、指定日期授权、管理员审计表；审计表有禁止 UPDATE/DELETE 的触发器。
- `future/server/src/repository.ts`：按账号行 `SELECT FOR UPDATE` 串行化并发写入；比较版本与稳定 JSON 摘要，以事务提交备份+幂等回执；过期客户端必须看到冲突，不偷偷覆盖别人记录。
- `future/server/src/ledger.ts`：补足对简记事件新增/编辑/删除、旧文本及元数据的校验，不能篡改旧历史却保持数字一致。
- `future/server/src/adminRepository.ts`：先从数据库核对员工角色、案件及限时授权，再**在同一事务中先写审计**，才可提取指定日期正文。审计写入失败，整个访问失败。SQL 查询使用参数绑定。
- `future/cloud/stableJson.ts`：云端摘要采用与字段序无关的稳定 JSON，以免 PostgreSQL `jsonb` 改变字段顺序造成误报。**不修改 v0.4 JSON 备份的 SHA-256 格式**。
- `future/server/tests/check-postgres.mjs`：使用独立真实 PostgreSQL 测试数据库验证并发竞争、按人隔离、幂等、数据一致性、恶意简记、禁止普通管理员读正文、审计失败拒绝泄露和删除。CI 另起 `postgres:16-alpine` 测试服务，不连接生产数据库；在 Mac 本地使用一次性 PostgreSQL 17 容器通过。
- 后端 `pg` 依赖有独立 lockfile， npm 官方 2026-10-16 审计该后端依赖树报告 0 项已知漏洞；**不等于整个 uni-app 主工程没有漏洞**，v0.4 的依赖审计阻断项保留。

**未完成不能绕过的门槛**：真实微信/手机号身份认证、生产数据库最小权限角色的部署验收、密钥管理、数据库加密、不可随意篡改的独立日志、数据副本清理、接口请求大小/速率限制、云端主体/备案/隐私要求及用户可见恢复界面。因此仍然**没有公开 HTTP 服务、真实云账号或任何用户数据上传**。细节参见 `future/server/README.md`。

## 6.1 数据库权限与会话验证补强（2026-10-16）

后端已补齐两个关键基础边界，但仍属未部署实现：

- `future/server/sql/002_runtime_permissions.sql` 建立独立运行时角色。备份数据库登录无法查询员工工单/审计，管理员运行时角色**没有对全量云快照表的直接 SELECT 权限**，只能执行按案件、日期与授权核查的 `cloud_read_day` SQL 函数。函数先插审计才可返回指定日期正文；禁用员工/审批人、关单或撤销授权都立即影响查询。
- `future/server/src/sessionTokens.ts` 与 `authenticatedService.ts` 实现短期签名会话及跨用途隔离；普通用户会话与管理员会话的密钥必须不同，管理员会话最多 5 分钟且要求近期 MFA。**这并不实现微信/手机号身份核验本身**，也不提供公开 HTTP API。
- `getCloudBackupStatus` 供未来用户查看是否开启、服务器备份版本与最后成功写入时间。未提交不应显示“已同步”，关闭同步也不意味着自动删除云快照。
- 本地真实 PostgreSQL 低权限账号与可控工单并发测试目前覆盖 **79 项**；独立会话验证覆盖 **36 项**。云端 CI 用 PostgreSQL 16 再次验收，相关用户文件与密钥均为合成测试数据。
- 生产上线所缺的供应商、密钥轮换与会话注销、法律授权、独立防篡改审计、数据库加密等仍是阻断项。详细列表见 `CN_CLOUD_BACKEND_SECURITY_HANDOFF.md`。

## 6.2 微信身份映射与撤销（独立工程）

`future/server/sql/003_wechat_identity.sql` 和 `src/wechatIdentity.ts` 实现了服务端微信临时代码验证接口的预留、HMAC 身份映射、并发初始化和重复 code 拒绝；`004_session_revocation.sql`、`src/sessionRevocation.ts` 支持单令牌服务端撤销，签名验证可在原 TTL 内兼容前任密钥以便轮换。管理员与普通会话仍使用不同密钥，身份运行时数据库账号无读取备份或删除用户权限。

这不是实际微信登录已通过验收，也没有手机号短信认证、生产密钥托管或公开 API。隔离后端已有账号级强制全设备退出，但尚无设备管理 UI。真实 PostgreSQL 集成检查已扩展到 **225 项**。详细技术/安全边界见 [微信登录与会话交接](CN_CLOUD_WECHAT_AUTH_HANDOFF.md)。

## 6.3 账号注销与限定后台留存（隔离 PostgreSQL）

新增 `sql/005_account_cancellation.sql`、`src/accountCancellation.ts`、`src/deletionReporting.ts`，以及真实数据库测试：服务端按已验证用户会话和明确二次确认，使用隔离 deletion 数据库角色原子化注销。云端正文、修改历史、微信身份和授权案件被删除；原访问审计仅留工作人员行为，抹去用户、具体日期与案件标识。只读 reporting 角色可看不关联个人的**月度注销账号数与擦除备份数**，不能读取私人内容。

短期墓碑用于阻断签名尚未到期的旧会话；已实现维护入口清理超过 24 小时的墓碑、旧微信登录 code 摘要及过期撤销记录。真实 PostgreSQL **225 项**集成检查通过。当前数据库中删除不等于物理备份/WAL/缓存均已及时删除，正式供应商数据生命周期与明确法定例外尚待评估。详见 [注销与留存规则](CN_ACCOUNT_CANCELLATION_POLICY.md)。

## 7. 早期合同原型（仍保留）

- `future/cloud/snapshotContract.ts`：纯内存服务器协议模拟，主动开启标记、owner 隔离、幂等、冲突、历史保全；**没有 HTTP、账号、数据库或自动上传代码**。
- `future/cloud/adminAccessContract.ts`：授权决策原型；不暴露真实管理后台或读取接口。
- `tests/check-future-cloud-contracts.mjs`：使用虚构记录模拟多个账号、并发/重放/篡改及员工权限失败情形；独立运行与 CI 持续验证。
- 两个合同模块不在 `src/` 内，不会被 H5/小程序打包；v0.4 首发仍只使用本地 `Records` 和用户主动的 JSON 备份。

**进入真正后端开发的门槛**：先确认主体和云供应商选型、正式账号能力、隐私/授权模型，以及完整事务、数据删除、日志与权限测试方案。不得用这个原型对真实用户开放云备份。

## 7.1 云备份恢复预检和冲突保护（独立合同）

`future/cloud/recoveryPlan.ts` 在恢复前校验云备份账号归属、修订号和内容 SHA-256，给出不含私人正文的本地/云端记录摘要。只有本地真正空白才显示可直接选择恢复；已记录数字、明确的 0、纯简记、主题设置等任何本地差异都进入手动冲突处理，**绝不自动覆盖或自动合并**。恢复本机前需用户输入明确确认；存在本地差异时还需用户完成并确认保存当前本地 JSON 备份。确认后仍重新比对本地/云端摘要与版本，过期预览拒绝写入。预检纯函数只返回候选记录；新增隔离的 `recoveryStorage.ts` 会先持久保存原数据日志再写入并验证新主记录，写入失败尝试回滚，异常中断可检查与人工接续；**没有接入真实 UI，不能将模拟存储当作小程序断电原子性验收**。详见 [恢复流程交接](CN_CLOUD_RECOVERY_HANDOFF.md)。

## 2026-10-18 · v0.5 本地历史首次上云迁移（P1 正式产品核心）

用户已明确：手动 JSON 恢复只是 v0.4 过渡手段，**最终产品必须自动云备份、多设备同步**。为避免老用户首次登录就丢失既有数据，新增独立的纯函数预检合同 `future/cloud/initialMigration.ts`，对应 `npm run test:future:first-link`。

- **首次迁移**：用户身份由经过服务端验证的会话给出，单独启用云备份并确认后，云账号没有已有快照、当前设备有实际本地内容，才能准备完整 `Records` 上传。数字、明确 0、简记与历史旧文字、操作时间及所有事件都一同迁移；只同步每天的最终数字是不合格的。
- **不覆盖云端或本地**：如果同账号云端已经有不同记录，返回手动冲突处理；空白设备已有云备份须走独立的安全恢复流程；两个设备竞跑首传时，事务级 `baseRevision=0 / baseDigest=null` CAS 只能成功一方，另一方得到冲突而不覆盖。对照当前本地与已知云快照摘要发现变化就拒绝使用旧预览上传。
- **防假成功**：上传回执不等于已经安全备份。必须从经认证的云端再读回并核对完整快照、所有历史、摘要及版本；若网络往返期间本地又有新增操作，状态为“首次上传成功但仍有本地改动待同步”，**不能显示“已同步”**。重试使用原有幂等键，不重复新增云端版本。
- **没有网络调用或默认授权**：这份合同不接入 v0.4 客户端，也不发 HTTP、不持久化本机、不创建微信登录或生产数据库。服务端仍必须强校验事件账本、令牌、并发、存储加密、访问控制、注销/副本清理及用户知情同意；纯函数测试不能替代真实数据库、跨设备端到端和正式微信 AppID 验收。
- **验收要求**：登录后原设备离线写入、网络失败重试、服务端成功但回执丢失、两设备首次关联、老设备已有数据与云端不一致等场景均需要实际前后端整体验收，且迁移中绝不能删除当前本地原件。

此合同作为 [Draft PR #4](https://github.com/ysr666/cuoshi/pull/4) 后续云同步开发入口，绝不提前并入 v0.4 [Draft PR #5](https://github.com/ysr666/cuoshi/pull/5)。

## 2026-10-19 · v0.5 日常自动云备份同步协议（P1）

隔离模块 `future/cloud/automaticSync.ts` 实现日常记录变化后的**单次自动同步协调器**（通过外部注入的云传输与本地耐久队列；不发网络请求、不读取真实用户）。新的 `npm run test:future:auto-sync` 目前覆盖 57 项正常、断网、读回不一致、重入和多设备冲突断言；该模块**尚未接入正式 v0.4 微信小程序**。

协议关键约束：

1. **账号首次上云只能走明确授权的首次迁移**。只有 `createLinkedJournal()` 基于已认证云端读回、与本地完整摘要一致的历史快照初始化版本游标后，自动同步才允许运行。无游标不得偷偷把用户本机笔记上传到新账户，用户关闭云备份时立即禁止发送。
2. **先耐久落盘待上传快照，再联网**。本机上传队列包含先前已验证的服务端 revision+digest、完整 `Records`、同一个幂等请求号。存储层写入失败或静默丢弃时直接拒绝上传；重启、断网、服务端已保存但响应丢失时，只重放相同请求，避免再次生成另一条修改历史。
3. **严格按事件完整快照与修订号 CAS 上传**。远端已有新修订、两个设备同时写入、旧历史事件被改写/截断，均停止自动上传并提示冲突；绝不 silent last-write-wins。为了避免连续触发同一适配器重入，含内部单飞锁；正式微信需另外使用单实例队列/持久锁，避免跨生命周期的多实例重复任务。
4. **成功需匹配服务端实际读回，而不只是上传回执**。验证 owner、修订号、stable digest、全量事件/记录内容；对账结果不一致时阻断自动重试并保留待处理快照。上传过程中有新本地事件时状态为待同步，随后另起一轮备份；不能虚报全部同步。
5. **仍缺生产前置能力**：正式微信身份服务与短期令牌刷新、隐私授权 UI、网络传输适配与限流/指数退避、跨页面持久队列锁、冲突解决界面、客户端上云撤销与注销闭环、单元/数据库/跨真机 E2E。严格禁止将纯合同测试宣称成已经提供自动云备份。

为保护早期用户，现在的单次协调器专门选择**遇到分叉就暂停**，不提供未经验证的事件级自动合并；后续如引入事件合并，必须独立证明所有旧文字与操作时间都不会丢失。

## 2026-10-19 · 微信客户端同步接线层（仍仅隔离研发）

新增 `future/cloud/clientAdapters.ts`，使前述 `automaticSync.ts` 不必依赖某个云供应商或具体微信 AppID。通过**显式注入**的 `uni.getStorageSync/setStorageSync`、`uni.request`、已认证短期令牌、当前本地 `Records` 读取函数与安全随机请求号函数构建客户端适配器。此模块不直接调用全局 `uni/wx`，不会自动启动网络或登录，不在首发小程序中。

## 2026-10-19 · 客户端到 PostgreSQL 的 HTTP 备份接口（不对公网开放）

隔离模块 `future/server/src/backupHttp.ts` 提供固定 `GET/PUT /v1/backup/snapshot` 路由的 **Node.js 请求处理函数**，与客户端 `clientAdapters.ts` 的固定 HTTPS 协议保持一致。它**没有创建监听器、没有登录/发令牌后门、没有部署程序与正式域名**。未来必须由具有有效 TLS、反向代理配置与可信微信 code2Session 登录的宿主程序显式挂载。

- **身份不从请求体获取**：只接受 Authorization Bearer 短期 token，真正用户身份由服务端 `AuthenticatedCloudService` 验签、数据库会话撤销及账号代际号验证后确定。请求必须正好包含 `baseRevision/baseDigest/idempotencyKey/records` 四项，额外 `ownerId/userId/token` 等字段一律拒绝；不通过 URL query、前端断言或 HTTP header 的任意 userId 选择账号。
- **拒绝不合法输入**：PUT 限 `application/json; charset=utf-8`，请求体 11 MiB 上限，超限在 JSON 解析前拒绝，UTF-8 严格解码；路径、方法、Content-Length 异常直接拒绝。错误响应不携带原始令牌、私密简记、SQL 错误或服务器堆栈。
- **客户端协议语义**：GET 200 返回本人 `CloudSnapshot`，204 表示尚未有备份；PUT 200 返回 `accepted/replayed` 幂等回执，409 返回 CAS revision/digest 冲突，400/401/403/422 为对应客户端错误。所有结果带 `Cache-Control: no-store` 等隐私头，不开放通配 CORS。
- **安全验收**：`npm run test:future:backup-http` 仅在 `127.0.0.1` 随机端口临时启动模拟服务器，以 24 项 HTTP/JSON/认证/大文件/完整历史场景验证与真实客户端备份适配器的一致性；在 `future/server/tests/check-postgres.mjs` 增加使用 PostgreSQL 最小权限角色的真实 HTTP GET/PUT/重复请求/CAS 冲突检查。**测试仍不能证明已生产上线**。
- **剩余生产门槛**：真实 HTTPS 证书、域名白名单、服务端 Host/Origin 策略、请求限流/超时、日志脱敏、审计/KMS、数据库备份及账户删除保留策略、真正微信会话刷新与多设备真机回归；未完成前不能挂公共监听或承诺云备份可用。

此模块只在 [v0.5 云研发 Draft PR #4](https://github.com/ysr666/cuoshi/pull/4)，不进入 v0.4 首发包。

**首次使用仍需一次透明的隐私告知及主动确认**：清楚列出每日数字、可选简记、完整修改历史会上传云端，确认后后端授权开启并默认自动同步。不能在用户毫不知情时上传私人正文；有权限登录不等于已经同意上传。后续正常保存、打开小程序、网络恢复，无须逐次确认；自动执行事件分别为 `onLocalSaved`、`onForeground`、`onNetworkRestored`。由 `future/cloud/cloudFirstLifecycle.ts` 的**注入式事件桥接**在实际 v0.5 微信宿主中连接“本地持久保存成功事件”、应用 `onShow`、`uni.onNetworkStatusChange` 等，销毁时取消订阅以防重复任务。

`future/cloud/cloudFirst.ts` 将已验证的首次迁移队列、设备账户游标、CAS 自动同步与云端读回组成云端优先状态机：初次授权后首次有记录就自动建立云备份，编辑后自动同步；网络异常时本机记录留存，显示“暂未同步”，网络恢复后重放原幂等请求；新设备本地为空时可以从有可信 owner/digest 的云端快照加载；本机**没有尚未上传修改**且云端版本更新时按云端为准自动拉取，并验证更新后的本机持久内容和同步游标。

**不能把“默认云端”误写成“无条件云端覆盖”**：如果本机仍有尚未上传的修改，且服务器已由另一台设备更新，停止自动覆盖并把本机记录保留为待处理，不抛出复杂冲突界面或自动合并，更不静默丢数据。真正的本机原子替换、未提交草稿保留、登录态管理必须由正式微信宿主提供经验证的适配；模拟器只验证合同，不代表上线环境已满足这些前置条件。
