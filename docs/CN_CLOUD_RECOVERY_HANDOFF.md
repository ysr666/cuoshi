# 错事 · 云备份恢复安全流程（未来版本）

> 本文为独立纯逻辑与自动化验收合同，**尚无真实云账户、服务器或小程序恢复 UI**。不会改变 v0.4 本地 JSON 备份逻辑。

## 已实现

- `future/cloud/recoveryPlan.ts`：验证经过认证的账号 ID、云快照修订号、完整内容与摘要；生成只含日期数、明确 0、纯文字日、简记数与历史事件数的预览。
- 本机空白、云端不存在、两端完全相同、两端存在差异分别呈现不同状态，不将**明确 0**误判为未记录，不将纯文字简记误判为无数据。
- 本机只要存在记录或未同步的主题偏好，就不静默覆盖；必须由用户明确选择用云备份替换本机，并输入确认文本。
- 本机与云端冲突时，必须先完成本地 JSON 导出并确认已安全保存；校验该文件结构和 SHA-256 与当前本机快照一致。恢复前再次核对本地/云端内容和云版本，变更后直接拒绝过期预览。
- 不自动合并 divergent 历史，更不会删除云端另一设备的修改。恢复预检只返回**深拷贝**的候选记录；另有**隔离的同步存储适配器及故障日志**，仍然没有连接实际小程序 UI。
- 自动测试覆盖：账号不匹配、摘要损坏、旧版本预览、零/空白/纯文字区分、历史保留、未导出本机冲突、不正确确认、深拷贝与本机写入中断。

## 新增：未来恢复的本地持久化故障防护

新增 `future/cloud/recoveryStorage.ts`，**它还没有被 v0.4 应用引用，也不是已经上线的云恢复功能**：

1. 在任何覆盖本机记录之前，重新读取磁盘记录并核对恢复预览的原始摘要；本机内容变化则拒绝。
2. 在临时恢复日志 `cuoshi-future-restore-journal-v1` 保存原始记录和草稿的可恢复副本并读回验证；写入日志失败则**绝不触碰主记录**。
3. 更新主记录 `cuoshi-uni-v1` 后重新读取验证；写入失败时尝试回滚，只有主记录成功校验后才移除旧草稿。
4. 如果主记录可能已经替换、但草稿或日志清理中断，明确返回 `cleanupPending`；下一次运行可判断 `original_present` / `replacement_present`。原始数据与新数据都不匹配或日志损坏，则返回 `manual_recovery_required` 并禁止自动覆盖。
5. 最难的故障场景（主记录写成无效数据、回滚再次失败）也必须保留恢复日志里的原始内容，不得误报恢复成功。

**67 项**纯合同／模拟存储故障检查通过。日志含明文私密记录的临时本机副本：必须按状态及时清理，不能上传云端或写入监控。模拟同步存储测试不能证明真实微信的闪存写入具有事务原子性；生产仍需验证微信容器断电/杀进程、存储容量不足、异常重启、隐私保护和恢复 UI 在真实设备上的表现。

## 仍需上线前验收

微信真实登录、云端上传/下载接口、用户主动开启、恢复 UI 与安全区/键盘处理、JSON 确实保存或发送成功、存储故障的微信真机恢复一致性、跨设备冲突处理及真机测试。**没有任何自动上传或覆盖用户现有数据的功能。**

与已完成的本地微信备份功能不同，云恢复必须同时核对真实服务器账号所有权、云快照版本以及同步状态，不得仅依赖前端传入的用户 ID。
